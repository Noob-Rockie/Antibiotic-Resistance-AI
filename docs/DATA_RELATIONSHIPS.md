## 1. The identifier hierarchy

All five files share the same three identifier columns:

| Column | Level | Distinct values | Notes |
|---|---|--:|---|
| `anon_id` | Patient | 283,715 | De-identified patient key. 53.834% of patients have more than one culture order (max 175). |
| `pat_enc_csn_id_coded` | Encounter | 574,584 | 1.3072 culture orders per encounter on average. |
| `order_proc_id_coded` | Culture order | 751,075 | **The single join key used by the whole pipeline.** |

`order_proc_id_coded` is nested strictly inside encounter, which is nested inside patient, so the triple `(anon_id, pat_enc_csn_id_coded, order_proc_id_coded)` and `order_proc_id_coded` alone identify exactly the same set of culture orders. The pipeline therefore joins on the single column and carries `anon_id` only as split metadata.

**Consequence for evaluation.** Because 53.8% of patients contribute more than one culture order, a naive random row split would place the same patient on both sides of the split and inflate every metric. All splits in this project are grouped by `anon_id`. See `docs/ML_PROBLEM_DEFINITION.md`.

## 3. Relationship cardinality and coverage

Measured by comparing key sets — no merge was executed to obtain these numbers.

| From | To | Cardinality | Cohort orders matched | Max rows per key on the right |
|---|---|:-:|--:|--:|
| `cohort` | `demographics` | N:1 | 751,075 (100.0%) | 1 |
| `cohort` | `labs` | N:M | 492,659 (65.5938%) | 106 |
| `cohort` | `resistance` | N:M | 166,537 (22.1732%) | 483 |
| `cohort` | `prior_med` | N:M | 575,344 (76.6027%) | 748 |

Reading of the table:

* **demographics** is the only genuine 1:1 companion — every one of the 751,075 culture orders has exactly one demographics row, and there are no orphans in either direction. It is safe to join directly.
* **labs**, **resistance** and **prior_med** are all one-to-many against the culture order. Joining any of them directly onto the cohort would multiply the label rows — up to 483x for `resistance` and 748x for `prior_med`. Each is therefore **aggregated to one row per key before it is joined**, never joined raw.
* Coverage is partial and is modelled explicitly: only 65.5938% of orders have any lab result, 76.6027% have prior medication history and 22.1732% have prior resistance history. Rather than imputing a fictitious history, the pipeline adds explicit `has_labs`, `has_prior_med_history` and `has_prior_resistance_history` indicators and fills count features with 0 (a true zero: no recorded prior event).

## 4. Join protocol enforced in code

`scripts/04_build_analytic_dataset.py` routes every merge through `validated_merge()`, which refuses to run unless the join is provably safe:

```python
def validated_merge(left, right, on, how, name, expect_right_unique=True):
    # 1. right side must be unique on the join keys, else refuse
    # 2. count how many left rows actually match
    # 3. execute the merge
    # 4. assert the row count did not change; raise if it did
```
